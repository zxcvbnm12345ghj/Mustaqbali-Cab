# مستقبلي كاب — Mustaqbali Cab

تطبيق ويب تقدمي (PWA) لحجز الرحلات بأربع خدمات: تاكسي، سيارة خاصة، توصيل طرود، ورحلات بين
المدن — بتجربة شاشة واحدة على طراز Uber/Careem (خريطة كاملة الشاشة + قائمة سفلية منزلقة)،
ولوحة إدارة منفصلة تماماً. مبنية بـ HTML / CSS / JavaScript بدون أي framework، تستخدم
Supabase كقاعدة بيانات ومصادقة، وتُنشر على Netlify.

## البنية

```
├── index.html            تطبيق العميل (PWA بشاشة واحدة: خريطة + قائمة سفلية)
├── request.html           إعادة توجيه فقط (توافق مع روابط قديمة) → index.html
├── admin.html              لوحة الإدارة (منفصلة تماماً عن تطبيق العميل)
├── manifest.json            بيانات تثبيت التطبيق (PWA)
├── sw.js                     Service Worker — يخزّن واجهة التطبيق للعمل والتثبيت بلا اتصال
├── icons/                    أيقونات التطبيق (192/512 عادية وmaskable + apple-touch-icon)
├── css/
│   ├── style.css              الرموز التصميمية المشتركة (ألوان/خطوط) + تنسيقات لوحة الإدارة
│   └── app.css                 تنسيقات تطبيق العميل فقط (الخريطة، القائمة السفلية، الشاشات)
├── js/
│   ├── config.js               إعدادات Supabase (عدّل القيم هنا)
│   ├── app.js                   منطق تطبيق العميل بالكامل (خريطة، قائمة سفلية، إرسال، حالة)
│   └── admin.js                 منطق لوحة الإدارة (بدون تغيير)
├── schema.sql                    مخطط قاعدة البيانات وسياسات RLS (بدون تغيير)
├── netlify.toml                   رؤوس أمان HTTP + إعدادات النشر
└── supabase/functions/notify-whatsapp/index.ts   دالة إرسال واتساب للإدارة (اختياري، لم تُبنَ بعد)
```

## 1) إعداد Supabase

1. أنشئ مشروعاً جديداً على [supabase.com](https://supabase.com).
2. من **SQL Editor** نفّذ محتوى ملف `schema.sql` بالكامل — سينشئ الجداول الأربعة (`trip_requests`،
   `trip_status_history`، `whatsapp_notifications`، `admins`) مع سياسات RLS المناسبة (الزوار
   يمكنهم الإرسال فقط عبر دالة RPC، والمشرفون المسجّلون يمكنهم القراءة والتحديث).
3. من **Authentication → Users** أنشئ مستخداً واحداً على الأقل (بريد وكلمة مرور) — هذا سيكون حساب المشرف لتسجيل الدخول إلى `admin.html`. ثم انسخ **User UID** الخاص به وشغّل في SQL Editor:
   ```sql
   insert into admins (user_id) values ('paste-the-user-uid-here');
   ```
   تسجيل الدخول بحد ذاته لا يمنح صلاحية الإدارة — الوصول مقيّد بجدول `admins` فقط (راجع قسم "مراجعة الأمان" أدناه).
4. من **Project Settings → API** انسخ:
   - `Project URL`
   - `anon public key`
5. الصق القيمتين في `js/config.js`:
   ```js
   const SUPABASE_URL = 'https://xxxx.supabase.co';
   const SUPABASE_ANON_KEY = 'eyJ...';
   ```

⚠️ لا تضع مفتاح `service_role` في الواجهة الأمامية أبداً — استخدم فقط `anon public key`.

## 2) التشغيل محلياً

لا حاجة لأي بناء (build). فقط افتح المشروع بخادم ملفات ثابت، مثلاً:

```bash
npx serve .
# أو
python3 -m http.server 8080
```

## 3) النشر على Netlify

- **Drag & Drop**: اسحب مجلد المشروع إلى [app.netlify.com/drop](https://app.netlify.com/drop).
- **Git**: اربط المستودع بـ Netlify، مع الإعدادات التالية:
  - Build command: (فارغ — لا يوجد بناء)
  - Publish directory: `.`

بما أن `js/config.js` يحتوي على `anon key` وهو مفتاح عام آمن للنشر في المتصفح (محمي بسياسات RLS)، لا حاجة لمتغيرات بيئة خاصة لتشغيل الموقع.

## تجربة العميل (تطبيق شاشة واحدة)

`index.html` هو التطبيق بالكامل — لا تنقّل بين صفحات. كل شيء يحدث داخل شاشة واحدة:
خريطة كاملة الشاشة (Leaflet + خرائط OpenStreetMap/CARTO المجانية بدون مفتاح API) وقائمة
سفلية (bottom sheet) قابلة للسحب بين ثلاث حالات ارتفاع (مطوية / نصف / كاملة). التنقّل بين
"اختيار الخدمة" → "تفاصيل الرحلة" → "حالة الطلب" يتم بتبديل المحتوى داخل نفس القائمة
السفلية عبر JavaScript، دون أي إعادة تحميل لصفحة جديدة.

**قابل للتثبيت (PWA):** بفضل `manifest.json` و`sw.js`، يمكن للعميل إضافة التطبيق لشاشته
الرئيسية (Android: "إضافة إلى الشاشة الرئيسية"، iOS Safari: "إضافة إلى الشاشة الرئيسية" من
قائمة المشاركة) ليعمل بواجهة تطبيق كاملة (بدون شريط عنوان المتصفح).

## لوحة الإدارة

- تسجيل دخول عبر Supabase Auth (بريد/كلمة مرور)، مقيّد بجدول `admins`.
- إحصائيات فورية: الإجمالي، طلبات جديدة، قيد التنفيذ، مكتملة.
- تصفية وبحث في الطلبات (بحد أقصى 300 طلب مُحمَّل)، وتعيين السائق، وتحديث حالة كل طلب عبر
  الجدول الزمني (جديد → تم التعيين → قيد التنفيذ → مكتملة/ملغاة).

## مراجعة الأمان (ملخص)

📋 **قبل النشر، راجع [`DEPLOYMENT_CHECKLIST.md`](./DEPLOYMENT_CHECKLIST.md) بالكامل.**

- **إرسال الطلبات العامة**: الزوار لا يملكون أي صلاحية INSERT/SELECT مباشرة على `trip_requests`. الإرسال يمر حصراً عبر دالة `submit_trip_request()` (SECURITY DEFINER) التي تقبل حقولاً محددة فقط وتضبط الحالة دائماً على `new`.
- **صلاحية الإدارة**: القراءة والتحديث على `trip_requests` و`trip_status_history` و`whatsapp_notifications` مقيّدة بدالة `is_admin()` التي تتحقق من وجود المستخدم في جدول `admins` — وليس مجرد كونه مسجّل الدخول. تسجيل حساب جديد عبر Supabase Auth وحده لا يمنح أي وصول لبيانات العملاء.
- **مفتاح anon**: آمن للنشر في المتصفح (`js/config.js`) لأن كل الحماية الفعلية تتم عبر RLS + جدول `admins`، وليس عبر إخفاء المفتاح.
- **مفتاح service_role**: لا يظهر في أي كود جهة العميل؛ محجوز لاستخدام مستقبلي داخل Edge Function خاصة بواتساب (لم تُبنَ بعد).

## مزايا الإصدار 1.1

### رقم الطلب التلقائي
كل طلب يحصل تلقائياً على رقم مرجعي بصيغة `MSQ-YYYYMMDD-0001` يُنشأ داخل قاعدة البيانات (trigger)، ويظهر في صفحة التأكيد وفي لوحة الإدارة.

### تحديد الموقع الحالي
عند فتح التطبيق، يحاول تلقائياً تحديد موقع الزائر الحالي (بصمت، بلا رسالة خطأ إن رُفض الإذن) وتوسيط الخريطة عليه، تماماً كتطبيقات الحجز الحقيقية. زر **"موقعي"** داخل حقل مكان الانطلاق، وزر التموضع العائم أعلى يمين الخريطة، وحتى سحب الدبوس نفسه على الخريطة أو النقر على أي نقطة منها — كلها تحدّث الموقع وتحوّله إلى عنوان نصي عبر خدمة [Nominatim](https://nominatim.org) المجانية (OpenStreetMap). الإحداثيات نفسها تُحفظ في `pickup_lat` / `pickup_lng`. المنطق بالكامل في `js/app.js`.

### تعيين السائق
من لوحة الإدارة، افتح تفاصيل أي طلب لإدخال اسم ورقم جوال السائق. تعيين سائق لطلب "جديد" ينقله تلقائياً إلى حالة "تم التعيين".

### الجدول الزمني للحالة
كل طلب يمر بأربع مراحل: **جديد ← تم التعيين ← قيد التنفيذ ← مكتملة** (مع إمكانية الإلغاء في أي مرحلة). يتم تسجيل توقيت كل مرحلة تلقائياً في جدول `trip_status_history` عبر trigger، ويُعرض كجدول زمني مرئي داخل تفاصيل الطلب في لوحة الإدارة. في شاشة العميل، يظهر نفس هذا التسلسل بصرياً داخل "حالة الطلب" مباشرة بعد الإرسال (دائماً "جديد" فور الإرسال، بصدق دون بيانات وهمية) — تحديثات الحالة اللاحقة تصل للعميل حالياً عبر واتساب فقط.

### إشعارات واتساب
- **للعميل (فوري، بدون إعداد إضافي):** بعد إرسال الطلب تظهر زر "تواصل عبر واتساب" داخل شاشة "حالة الطلب" يفتح محادثة مباشرة مع رقم الشركة عبر رابط `wa.me` مع رسالة معبأة مسبقاً برقم الطلب والتفاصيل. عدّل `BUSINESS_WHATSAPP_NUMBER` في `js/app.js`.
- **للإدارة (اختياري):** كل طلب جديد يُضاف تلقائياً إلى جدول `whatsapp_notifications` عبر trigger. الإرسال التلقائي الفعلي لرقم واتساب الإدارة يتطلب بناء Edge Function (`supabase/functions/notify-whatsapp/index.ts`) — غير مبنية بعد في هذه النسخة، والقائمة تُملأ بالبيانات لحين تفعيلها.

### تجربة الجوال (App-shell)
- لا تنقّل بين صفحات إطلاقاً لدى العميل — خريطة كاملة الشاشة + قائمة سفلية واحدة تحمل كل الشاشات (اختيار الخدمة، تفاصيل الرحلة، حالة الطلب) دون إعادة تحميل.
- القائمة السفلية قابلة للسحب يدوياً بين ثلاث حالات ارتفاع (مطوية/نصف/كاملة) عبر Pointer Events، بالإضافة لتبديل تلقائي عند اختيار خدمة أو فتح النموذج.
- حجم خط 16px لكل حقول الإدخال لمنع تكبير Safari التلقائي عند التركيز، ومساحات لمس ≥ 48px لكل الأزرار والدبابيس.
- بطاقات زجاجية (glassmorphism) مع `backdrop-filter: blur()` على شريط العلامة التجارية العلوي، أزرار التموضع العائمة، والقائمة السفلية نفسها.
- على الشاشات الأوسع من الجوال (≥640px)، تتحول القائمة السفلية تلقائياً لبطاقة عائمة بعرض ثابت بدل أن تمتد لكامل العرض.

## أفكار للتوسّع لاحقاً

- تتبّع مباشر لموقع السائق عبر Supabase Realtime.
- استعلام حالة الطلب مباشرة من شاشة العميل (يتطلب RPC آمنة إضافية بصلاحيات محدودة تُعيد الحالة فقط لصاحب رقم الطلب).
- حساب سعر ديناميكي فعلي بالاعتماد على مسافة حقيقية (Google/Mapbox Distance API).
- تطبيق سائقين منفصل لقبول الطلبات وتحديث الحالة من الميدان.
- بناء Edge Function لإشعارات واتساب التلقائية للإدارة.
- ترقية مزوّد بلاطات الخريطة (Mapbox/Maptiler بمفتاح API) عند نمو حركة المرور — طبقة CARTO المجانية الحالية مخصصة للاستخدام المتوسط وليست بلا حدود.
